# 01 — 隱晦模型

> 這是本專案最重要的文件。所有實作決策都必須能回推到這裡的某一條規則。

## 一、問題重述

「隱晦」不是一個模糊的美學要求，它是一個可以拆解的工程問題。先釐清一件事：

**訊息內容藏不住。**

使用者必須能一眼讀懂訊息，這代表訊息必須以人類可讀的明文出現在螢幕上。任何「把訊息編碼成變數名稱、讓使用者心算解碼」的方案，都會讓閱讀成本高到工具失去意義——如果讀一則訊息要花十秒鐘解碼，那還不如直接開手機。

所以，能藏的不是內容，是這三件事：

| 軸線 | 藏什麼 | 手段 |
|---|---|---|
| **形式** | 訊息長得不像訊息 | 讓它長得像 git blame、lint 警告、LSP hover、quickfix 結果 |
| **時間** | 訊息幾乎不存在於畫面上 | 預設不顯示，只在使用者主動注視時短暫出現，然後自動消失 |
| **版面** | 訊息出現時畫面不跳動 | 不開視窗、不捲動、不增減行數、不移動游標 |

其中**時間軸線的效果遠大於形式軸線**。一段偽裝得再好的文字，只要常駐在畫面上，被看到只是時間問題；而一段每次只出現三秒、且只在使用者停下來時出現的文字，旁人根本沒有機會遇到它。

第三條「版面不變」則是最容易被低估的。人的餘光對「動態」極度敏感，對「靜態文字內容」則幾乎無感。一個突然彈出的浮動視窗，即使裡面寫的是程式碼，也一定會被隔壁桌注意到；而一行安靜出現在行尾的暗灰色文字不會。

## 二、威脅模型

**要防的：路過的同事與主管。**

具體來說：
- 從旁邊走過，往螢幕瞄一眼（0.5–2 秒，看到的是整體版面而非文字）
- 坐在隔壁桌，用餘光感知你的螢幕是否有異常動態
- 走到你旁邊問問題，看到你螢幕上停留的畫面

**明確不防的：**
- 站在你背後認真逐字讀螢幕的人
- 公司的螢幕錄影、MDM、鍵盤側錄、網路流量分析
- 螢幕分享 / 視訊會議中的錄影（有部分緩解措施，見第六節，但不保證）
- IG 端本身（對方看到的仍是正常已讀與回覆）
- 事後被人翻你的 nvim session 或 shell history

**使用者責任：** 本工具可能違反你所屬組織的規範。是否使用、在什麼場合使用，由使用者自行判斷與承擔。本專案不提供任何「規避公司政策」的功能（例如偵測並繞過監控軟體），也不會為此加入功能。

## 三、曝光分級 L0–L3

這是「隱晦」的核心操作定義。訊息的可見程度分成四級，使用者可以隨時在等級之間移動，也可以設定自動降級。

### L0 — 靜默（預設常駐）

畫面上**零變化**。

有新訊息時，唯一的訊號是 statusline 上一個**既有元素**的狀態改變。關鍵在於「既有」——不是新增一個未讀數字 badge（那是新元素，會被注意到），而是改變一個本來就在那裡的東西：

- LSP 狀態圖示由 `✓` 變成 `⟳`（看起來像 language server 正在索引）
- gitsigns 的變更計數多了幾個（`+3 ~1` → `+4 ~1`）
- 一個本來顯示 `spaces:2` 的區段短暫變成 `spaces:4`

這些變化只有知情者看得懂。旁人即使盯著 statusline 看，也只會覺得編輯器在做它平常做的事。

**L0 是預設狀態，也是 panic 之後回到的狀態。**

### L1 — 一瞥

游標所在行的右側，出現暗色右對齊的虛擬文字：

```
    if err != nil {                          mia · 3 分鐘前 · 晚上要吃什麼
        return fmt.Errorf("parse: %w", err)
    }
```

這是預設的收訊主通道，因為 **git blame 的語意與訊息的語意天然吻合**：

| blame 欄位 | 對應到 |
|---|---|
| 作者名 | 聯絡人（可設定別名） |
| 相對時間 | 訊息時間 |
| commit subject | 訊息內容 |

`gitsigns.nvim` 的 `current_line_blame` 幾乎人人都開，格式與位置完全一致，暗灰色低對比、右對齊、只在游標行出現、游標移動就重繪——連行為模式都一樣。這是整個專案裡最好的一個偽裝點。

**觸發時機至關重要：** 不在訊息到達時顯示，而是在 `CursorHold`（游標停止移動約 500ms）之後才顯示。理由是——使用者停下來時，眼睛已經在游標附近；此時出現的文字，使用者不需要移動視線就能讀到，而旁人的餘光也不會捕捉到「有東西冒出來」的動態，因為在他們的視角裡畫面是靜止的。

**消失時機：** 游標移動、進入 insert 模式、或逾時（預設 4 秒）。三者取其先。

### L2 — 閱讀

需要讀完整內容或看上下文時，按鍵開啟一個浮動視窗：

```
╭──────────────────────────────────────╮
│ mia   14:32                          │
│   晚上要吃什麼                        │
│ you   14:33                          │
│   都可以 你決定                       │
│ mia   14:35                          │
│   那去上次那間拉麵好了 七點           │
╰──────────────────────────────────────╯
```

樣式必須與該使用者環境中**真實的 LSP hover 視窗完全一致**：相同的 border 字元、相同的 highlight group（`NormalFloat` / `FloatBorder`）、相同的寬度上限與位置邏輯。實作上直接沿用 `vim.lsp.util.open_floating_preview` 的參數慣例，而不是自己刻一套外觀。

**關閉時機：** 游標移動、切換視窗、`FocusLost`、按下任意鍵。與真實 hover 的行為一致。

### L3 — 全景

整段對話歷史以 quickfix 列表呈現：

```
chat/mia.go|142 col 3| mia: 晚上要吃什麼
chat/mia.go|143 col 3| you: 都可以 你決定
chat/mia.go|145 col 3| mia: 那去上次那間拉麵好了 七點
```

一份 quickfix 列表在旁人眼中就是一份 lint 報告或搜尋結果，而且它**本來就是滿螢幕的文字**，不需要偽裝成別的東西。`:cnext` / `:cprev` 走過對話，操作手勢也完全正常。

檔名與行號是假的，僅供列表格式完整；跳轉行為必須被攔截（見第五節不變式）。

L3 是唯一會佔用大塊畫面的等級，只在使用者明確下指令時進入，且應設定較短的自動關閉時間。

### 等級之間的移動

```
        新訊息            停下游標          按鍵            指令
  L0 ──────────► L0 ─────────────► L1 ─────────► L2 ─────────► L3
   ▲   (只改暗號)         ▲                │             │
   └──────────────────────┴────────────────┴─────────────┘
              游標移動 / 逾時 / FocusLost / panic
```

**降級永遠比升級容易**——這是設計上刻意的不對稱。升級需要使用者明確動作，降級則有大量的自動觸發條件。

## 四、語意偽裝

即使形式對了，內容本身也可能刺眼。以下是內容層的處理規則：

### 一律移除 emoji

**emoji 是程式碼畫面上最大的破綻。** 一個彩色的 😂 出現在單色的程式碼區域，餘光一定抓得到，而且沒有任何合理解釋。處理方式：
- 常見 emoji 轉為 ASCII 顏文字（😂 → `:D`、❤️ → `<3`）
- 其餘一律刪除或轉為 `[emoji]`

### 聯絡人別名

顯示的作者名可設定映射，讓它看起來像一個真實的 git 作者或工具名：

```lua
aliases = {
  ["@mia:example.org"]  = "m.chen",     -- 看起來像同事帳號
  ["@alex:example.org"] = "alex.wu",
}
```

### 單行截斷

L1 只顯示單行。超過設定長度（預設 60 個顯示寬度單位）截斷並加 `…`。太長的訊息本來就不該在 L1 讀，那是 L2 的工作。

### 中文的處理

中文出現在程式碼註解、commit message、blame 內容裡對台灣的工程團隊完全正常，不需要特別處理。但要注意**顯示寬度計算**：中文字寬度為 2，截斷時必須用 `vim.fn.strdisplaywidth` 而非字元數，否則右對齊會跑掉——跑掉的排版比中文本身顯眼得多。

### 訊息不加標點裝飾

不要加 `>>`、`[NEW]`、`★` 這類標記。任何一個「不屬於這個 UI 元素本來會有的字元」都是破綻。blame 就用 blame 的分隔符（` · `），診斷就用診斷的格式。

## 五、不變式（硬性規則）

以下規則沒有例外，任何 renderer / composer 實作都必須遵守。程式碼審查時應逐條檢查。

### I1 — 永不寫入 buffer 文字

訊息只能透過 `nvim_buf_set_extmark` 的 `virt_text` 或 floating window 呈現，**永遠不透過 `nvim_buf_set_lines` 或 `nvim_buf_set_text` 寫入 buffer 內容**。

理由不只是隱晦，更是安全：只要訊息不在 buffer 裡，就不可能被 `:w` 存進檔案、不可能被 `git add`、不可能出現在 PR diff 裡。這是本專案最重要的一條規則——一則聊天訊息被 commit 進公司 repo，後果遠比被同事瞄到嚴重。

Composer 是唯一需要接受輸入的地方，因此**只能使用 cmdline 或 scratch buffer（`buftype=nofile`、`bufhidden=wipe`、`swapfile=false`）**，絕不可在使用者的真實檔案 buffer 上輸入。

### I2 — 永不改變版面

- 用 `virt_text` 而**不用** `virt_lines`——後者會插入視覺行、推擠下方內容、改變畫面上所有東西的位置
- 不開 split、不開 tab
- 不移動游標、不捲動畫面
- 浮動視窗只在 L2/L3 且由使用者明確觸發時出現
- 訊息到達時**絕不**自動做上述任何一件事

### I3 — 永不主動吸睛

- 無聲音（不呼叫任何 bell / notify）
- 無閃爍、無動畫、無 `vim.notify` 彈出
- highlight 一律 `link` 到既有的 group（`Comment`、`NonText`、`Conceal`、`DiagnosticVirtualTextHint`），**不自訂顏色**。使用者的配色方案已經調校過，任何自訂顏色都會與周圍格格不入
- 不使用粗體、底線、反白

### I4 — 永不落地

- 訊息內容只存在於 daemon 的 XDG state dir（權限 `0600`）與前端的記憶體中
- 前端不寫任何暫存檔、不寫 `shada`、不進 `:messages` 歷史、不進 `undofile`
- Composer 的草稿不寫入磁碟
- socket 位於 `$XDG_RUNTIME_DIR`，權限 `0600`

### I5 — 未經注視不呈現

任何等級的內容呈現，都必須由使用者的動作觸發（`CursorHold`、按鍵、指令），**絕不由訊息到達觸發**。訊息到達只能改變 L0 的暗號狀態。

## 六、Panic 與自動靜默

### 手動 panic

一個全域按鍵（預設不綁定，強制使用者自行選擇一個順手且不衝突的鍵），效果：

1. 清除所有 extmark 與浮動視窗
2. 關閉 quickfix（若由本外掛開啟）
3. 降到 L0
4. 進入靜默期（預設 10 分鐘），期間連 L0 暗號都不更新
5. **無任何回饋**——不顯示「已進入靜默模式」，因為那本身就是破綻

按鍵必須在 normal / insert / visual 模式都能用，且是單鍵或雙鍵組合——三鍵組合在緊急時按不出來。

### 自動觸發

| 事件 | 動作 | 理由 |
|---|---|---|
| `FocusLost` | 立即清空所有呈現 | alt-tab、有人叫你、切到瀏覽器 |
| `VimResized` | 降到 L0 | 接投影機、開始螢幕分享時解析度常會變 |
| `VimLeavePre` | 清空 | 離開前不留痕跡 |
| idle 逾時 | 降到 L0 | 離開座位時畫面上不該還留著東西 |
| 進入 terminal buffer | 不呈現 | terminal 裡出現 blame 文字非常突兀 |
| 非白名單 filetype | 不呈現 | 只在程式碼檔案裡呈現才合理 |
| `diff` 模式 / `man` 頁 | 不呈現 | 這些畫面上出現 blame 完全不合理 |

### 螢幕分享的部分緩解

無法可靠偵測螢幕分享（那需要平台專屬的程序偵測，屬於非目標）。提供的是：
- 一個明確的 `:QuietdmSilence <分鐘>` 指令，開會前手動進入
- `VimResized` 自動降級（涵蓋一部分情況）

**文件必須誠實告知使用者：螢幕分享時請自行手動靜默，不要依賴自動偵測。**

## 七、回覆通道

輸入比呈現更難偽裝，因為打字這個動作本身會持續數秒到數十秒，且旁人可能正好在看。

### 預設：cmdline 幽靈輸入

使用者按下觸發鍵，進入一個 cmdline 輸入（`vim.ui.input` 或 `getchar` 迴圈），提示符偽裝成常見指令樣式：

```
:%s/晚上七點拉麵店見/
```

優點：
- 在 cmdline 打字是 vim 使用者每分鐘都在做的事，動作完全正常
- 送出後自動清空，不留痕跡
- 位置在畫面最底部，離旁人視線焦點最遠
- 不佔用任何畫面空間，不改變版面

缺點：長訊息在 cmdline 編輯不方便（無法多行、方向鍵移動有限）。

### 備選：浮動輸入框

樣式與 LSP rename 提示框一致的單行浮動輸入。適合喜歡視覺焦點在游標附近的使用者。

### 備選：假 commit message

開一個 scratch buffer，`filetype=gitcommit`，看起來就是在寫 commit message。適合較長的回覆——在 commit message buffer 裡打好幾行中文，是完全正常的行為。存檔（`:w`）即送出，`:q` 即取消。buffer 必須是 `nofile`，永不落地。

### 送出後無回饋

送出成功**不顯示任何提示**。沒有提示本身就是隱晦。使用者若要確認，自己的訊息會在下一次 L1/L2 呈現時以自己的名字出現。

送出失敗才需要告知，且應偽裝成一個無害的錯誤（例如一則 `DiagnosticHint` 樣式的虛擬文字），而非 `vim.notify` 的紅色錯誤彈窗。

## 八、可插拔性

上述所有選擇都是**預設值，不是規定**。不同人的工作環境差異極大：有人的 statusline 上根本沒有 LSP 狀態圖示、有人不用 gitsigns、有人的公司座位是背對牆的（威脅模型完全不同）。

因此 Renderer / Composer / Notifier 都是介面，內建實作各自獨立，使用者可以：
- 換掉預設 renderer（例如改用診斷樣式）
- 同時啟用多個 renderer（L1 用 blame、L3 用 quickfix）
- 自己寫一個 renderer 註冊進來

介面定義見 [04-plugin-api.md](04-plugin-api.md)。

## 九、實作檢查清單

每個 renderer / composer 實作合併前，逐條確認：

- [ ] 沒有呼叫任何會修改 buffer 文字的 API（I1）
- [ ] 沒有使用 `virt_lines`、沒有開 split、沒有動游標（I2）
- [ ] 所有 highlight 都是 `link` 到既有 group，沒有自訂顏色（I3）
- [ ] 沒有寫入任何檔案，沒有進 `:messages`（I4）
- [ ] 呈現由使用者動作觸發，而非訊息到達觸發（I5）
- [ ] 註冊了 `FocusLost` / `VimLeavePre` 的清空處理
- [ ] 尊重 filetype 白名單與靜默狀態
- [ ] 截斷使用 `strdisplaywidth` 而非字元數
- [ ] emoji 已在呈現前被過濾
